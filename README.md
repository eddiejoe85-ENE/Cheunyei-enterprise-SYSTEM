# 進銷存系統：自架版（Firebase）安裝說明

這個資料夾是可以放到自己網站上的版本。資料存在你的 Firebase（Firestore），登入用 Firebase Authentication。
放在一般網站上時，「列印」可以直接跳出作業系統的列印視窗。

## 檔案
| 檔案 | 用途 |
|---|---|
| index.html | 系統本體 |
| firebase-config.js | **只要改這個**：貼上你的 Firebase 設定 |
| firebase-adapter.js、firebase-boot.js | 連接 Firebase 與登入畫面，不用改 |
| firestore.rules | 安全規則（要貼進你原本的規則，不要整份覆蓋；2026.10.02-b 起是加嚴版） |
| firebase.json | Firebase Hosting 設定 |

## 步驟

### 1. 填入 Firebase 設定
Firebase 主控台 → 專案設定（齒輪）→ 一般 → 你的應用程式 → 新增「網頁」應用程式 → 複製 `firebaseConfig`，貼到 `firebase-config.js`。
> 資料會放在 `inv_` 開頭的集合（例如 `inv_orders`、`inv_products`），不會動到你原本資料庫裡的集合。

### 2. 開啟登入
Authentication → 登入方式 → 啟用「電子郵件/密碼」。

### 3. 設定安全規則
（全新資料庫直接用 `firestore.rules.full` 整份取代；已有其他應用程式的規則才用 `firestore.rules` 合併。）
Firestore Database → 規則。把 `firestore.rules` 裡的三個 function 和兩段 `match` **貼進你原本規則的 `match /databases/{database}/documents { ... }` 裡面**，按「發布」。
（只有 `inv_` 開頭的集合會受影響。）

### 4. 建立第一個管理員（只需一次）
1. Authentication → 使用者 → 新增使用者，輸入 Email 和密碼，記下這個使用者的「使用者 UID」。
2. Firestore Database → 開始集合 → 集合 ID 填 `inv_users` → 文件 ID 貼上剛才的 UID → 新增欄位：
   - `name`（字串）：你的名字
   - `level`（字串）：`admin`
3. 之後其他人都在系統裡「更多 → 系統 → 登入帳號管理」新增，不用再進主控台。

權限層級：
- `admin` 管理員：可改商品與設定，可管理登入帳號
- `edit` 可編輯：開單、收付款、盤點等日常作業
- `view` 唯讀

### 5. 放上網站
**方法 A：Firebase Hosting（建議）**
```
npm install -g firebase-tools
firebase login
firebase init hosting     # public 目錄填 .（一個點），不要設成單頁應用，不要覆蓋 index.html
firebase deploy --only hosting
```
**方法 B：任何網站空間**：把整個資料夾的檔案上傳即可（要用 https）。
之後到 Authentication → 設定 → 已授權的網域，加入你的網站網址。

### 6. 搬移舊資料（如果原本在 Claude 裡已經有資料）
1. 在舊系統：更多 → 系統 → 資料庫備份 → 立即備份，存下 JSON。
2. 在新系統用管理員登入：更多 → 系統 → 資料庫備份 → 從備份還原 → 選檔案 → 選「全部寫回」。
3. 舊資料裡的成員代號和新登入帳號不同。到「成員與權限」重新指派每個人的角色與可用倉庫。舊單據上的建立者名稱會盡量從備份裡的成員名單帶回。

## 列印
- 一般瀏覽器（Chrome、Edge）開啟網站，按「列印」會直接跳出列印視窗，在那裡選 EPSON LQ-690C。
- 想按一下就直接出單、不出現視窗：把固定用的那台電腦上的 Chrome 捷徑加上 `--kiosk-printing`，並把 EPSON LQ-690C 設為預設印表機。
- 更多 → 列印診斷 可以檢查這個環境能不能列印。

## 注意
- 資料備份：Firestore 沒有自動備份，請定期用系統的「資料庫備份」，或到 Google Cloud 開啟排程備份。
- 費用：小型使用量通常在 Firebase 免費額度內；用量增加後才會計費，可以在主控台設預算提醒。
- 這份是在模擬環境測過，沒有連上你的真實 Firebase 專案。第一次啟動請先用測試專案或先備份，確認能登入、開單、重新整理後資料還在，再正式使用。

## 權限與成員可見度
- 只有管理員能列出全部成員、修改任何人的角色與登入層級；非管理員的畫面沒有「成員與權限」和「登入帳號管理」，資料庫規則也不允許他們列出成員名單或修改角色。
- 單據上的「建立者」名稱，其他人仍然看得到（用代號單筆查詢），只是拿不到完整名單。
- 更新規則後，非管理員第一次登入時系統會自動登記名字。

## 更新網站（系統有新功能時）

網站放在 GitHub Pages（`eddiejoe85-ene.github.io` 的 `firebase-deploy` 資料夾）。更新程式**只要換掉 `index.html` 這一個檔案**；`firebase-config.js` 等其他檔案、Firestore 裡的資料、登入帳號都不用動，也不會被清掉。

### 方法一：用 GitHub 網頁（最簡單，不用裝任何東西）
1. 把新的 `index.html` 存在電腦上（從我給你的檔案下載；或解開 `firebase-deploy.zip`，取裡面的 `index.html`）。
2. 登入 GitHub，打開 repository `eddiejoe85-ene.github.io`，點進 `firebase-deploy` 資料夾。
3. 右上角 **Add file → Upload files**，把新的 `index.html` 拖進去（檔名一樣，會直接覆蓋舊的）。
4. 頁面最下面按 **Commit changes**。
5. 等 1～2 分鐘。可以在 repository 的 **Actions** 分頁看「pages build and deployment」出現綠色勾勾，就是上線了。
6. 開網站，按 **Ctrl+F5**（手機：重新整理，或關掉分頁再開）。到「更多」最下面，看「**系統版本**」是不是新的版本號，有變就是更新成功。

### 方法二：用 git 指令
```
git pull
（把新的 index.html 複製到 firebase-deploy 資料夾，覆蓋舊的）
git add firebase-deploy/index.html
git commit -m "更新進銷存系統"
git push
```

### 方法三：如果你是用 Firebase Hosting
在放這個資料夾的電腦上：
```
firebase deploy --only hosting
```

### 更新後
- 看不到新畫面：多半是瀏覽器還在用舊的快取，按 Ctrl+F5。GitHub Pages 自己最多也會快取約 10 分鐘。
- 正在用系統的人，重新整理頁面就會換成新版。
- 更新前建議先到「更多 → 系統與設定 → 資料庫備份」按一次「立即備份」，萬一要退回舊版，資料也有一份。
- 想退回舊版：GitHub 上點 `index.html` → **History**，找到舊的版本，把它下載後再用方法一傳上去。

### 兩個地方的版本是分開的
- Claude 裡的版本：我每次修改後都會直接更新。
- 你自己的網站（GitHub Pages）：不會自動更新，要用上面的方法換 `index.html`。所以兩邊可能不同版本，看「更多」最下面的「系統版本」就知道。

### 安全規則（`firestore.rules`）要不要更新？
目前的規則是「所有 `inv_` 開頭的集合」通用，之後新增的功能（人員、考勤、薪資、拆解設定、代收單等）都已經涵蓋，**一般不用再改**。只有我特別通知「規則有變」時，才需要到 Firestore Database → 規則重新貼上並按「發布」。

### 自架版和 Claude 版的差別
- 自架版是用 Firebase 帳號（電子郵件和密碼）登入；系統裡新增的「員工編號＋打卡密碼」登錄是另外一層，管理員（Firebase 的 `admin`）預設可以直接進入，不用再登錄一次。
- 相機（上下班打卡拍照）、定位、語音都要用 **https**，GitHub Pages 本來就是 https，沒問題；第一次使用時瀏覽器會問你是否允許。

## 加嚴安全規則與管理員設定（版本 2026.10.02-b）

這一版把資料庫規則改得更嚴，**要照順序做**：

### 一、先換網站（index.html），再換規則
1. 先用上面「更新網站」的方法，把新的 `index.html` 傳上去，確認「更多」最下面顯示「系統版本 2026.10.02-b」。
2. **再**發布新的規則。順序反過來的話，舊版網站在非管理員身上會出現錯誤畫面。

### 二、發布新的規則
1. Firebase 主控台 → 專案 → Firestore Database → **規則**。
2. 如果這個資料庫只給進銷存系統用：把原本的規則全選刪除，貼上 `firestore.rules.full` 的全部內容。
   如果還有別的應用程式也在用：把 `firestore.rules` 裡的新內容，換掉原本進銷存（`inv_` 開頭）的那幾段。
3. 按 **發布**。
4. 用編輯器上方的 **規則遊樂場** 驗證幾項（身分選「已驗證」、填對應使用者的 UID）：
   - 唯讀（view）帳號讀 `inv_payroll/任意` → 應該 **拒絕**。
   - 可編輯（edit）帳號讀 `inv_payroll/任意` → 應該 **拒絕**。
   - 管理員（admin）讀 `inv_payroll/任意` → **允許**。
   - 可編輯（edit）帳號寫 `inv_employees/任意` → 應該 **拒絕**；管理員 → 允許。
   - 唯讀（view）帳號讀 `inv_attphotos/任意` → 應該 **拒絕**；可編輯 → 允許。
   - 可編輯（edit）帳號寫 `inv_prules/任意`、`inv_closings/任意` → 應該 **拒絕**；寫 `inv_orders/任意` → **允許**。

### 加嚴了什麼
| 資料 | 誰能讀 | 誰能寫 |
|---|---|---|
| 薪資彙總（inv_payroll） | 只有管理員 | 只有管理員 |
| 人員資料（inv_employees，含打卡密碼雜湊） | 有開通的登入帳號 | 只有管理員 |
| 上下班打卡照片（inv_attphotos） | 可編輯以上（唯讀帳號不能看） | 可編輯以上 |
| 商品、系統設定、期間封存、價格規則、庫存關帳 | 有開通的登入帳號 | 只有管理員 |
| 其他（單據、收付款、盤點、考勤、請假…） | 有開通的登入帳號 | 可編輯以上；唯讀帳號完全不能寫 |

### 對使用的影響
- **做薪資、管理人員資料的人，登入帳號層級要設成「管理員」**（見下一節）。「薪資」「人事」只是畫面上的分類，資料庫只認 管理員／可編輯／唯讀 三種層級。
- 一般員工（可編輯）：開單、收款、盤點、打卡、請假照常使用，不受影響；他們的畫面不會出現「獎金與薪資」，也不能新增、修改人員資料。
- **仍有的限制**：人員資料裡的「打卡密碼雜湊值」，有開通的登入帳號都讀得到，因為「員工編號＋打卡密碼」登錄、上下班打卡要用它來核對。請員工使用 6 碼以上的密碼，並只開通信任的人的 Firebase 帳號。

### 把某個人（例如王俊傑）設成管理員
**方法一：在系統裡改（建議）**
1. 用現有的管理員登入網站。
2. 更多 → 系統與設定 → **登入帳號管理** → 找到王俊傑 → 層級選「管理員」→ 儲存。

**方法二：在 Firebase 主控台改**
1. Authentication → 使用者，找到王俊傑的 Email，複製他的 **使用者 UID**。
2. Firestore Database → 集合 `inv_users` → 文件 ID 是那個 UID 的文件 → 把欄位 `level` 改成 `admin`。

改完後，請王俊傑**登出再登入**（或重新整理）才會生效。
> 管理員不受畫面上「使用者分類」限制，薪資、人員管理、價格策略、系統設定、期間封存等都能用。

## 登入帳號管理：編輯、刪除帳號（版本 2026.10.02-d）

這一版「更多 → 系統與設定 → 登入帳號管理」可以：新增、修改顯示名稱、改層級、寄重設密碼信、刪除帳號。

**更新時要換兩個檔案：`index.html` 和 `firebase-boot.js`。**
- 只換 `index.html` 也能用，只是「寄重設密碼信」的按鈕不會出現（其他功能都正常）。
- 兩個都換，才有完整功能。步驟和之前一樣：GitHub → Add file → Upload files → 把兩個檔案一起拖進去 → Commit changes。

**刪除帳號是什麼意思**
- 刪掉的是系統裡的權限紀錄（`inv_users`）。他登入後只會看到「帳號尚未開通」，什麼資料都讀不到；他以前開的單據和紀錄都會保留。
- Firebase 裡的登入帳號本身還在，要完全移除，請到 Firebase 主控台 → Authentication → 使用者 → 刪除。
- 不能刪除自己，也不能刪除最後一位管理員。
- 如果這個帳號綁定在某位人員（人員管理），刪除後那位人員改用員工編號登錄，權限分類保留。

**改密碼、改 Email**
- 系統（網頁）沒辦法直接改別人的密碼；他忘記密碼時，在帳號的「編輯」按「寄重設密碼信」，他自己從信裡設定新密碼。
- 要換 Email：建立新帳號，再刪除舊帳號。

## 登錄前看不到任何功能（版本 2026.10.02-e）

- 只要「系統登錄」是開啟的（預設開啟），**員工登錄之前，畫面上只有登錄框**：沒有選單、沒有功能名稱、沒有按鈕，連 Ctrl+K 搜尋也不能用。
- 還沒有任何人設定打卡密碼時，一般員工只會看到「目前還沒有人設定打卡密碼，暫時沒有人可以登錄，請通知管理員」。管理員（網站帳號是「管理員」層級）不受影響，可以直接進入，到「更多 → 人員管理」替員工設定員工編號和打卡密碼。
- 登錄畫面原本有一顆「只要上下班打卡」，預設已關閉。共用平板需要時，到「系統設定」勾選「登錄畫面也放一顆「只要上下班打卡」」。
- 管理員預設可以不登錄就進入；要連管理員也先登錄，在「系統設定」勾選「管理員也要登錄」。
- 整個登錄功能可以在「系統設定」關掉，關掉就回到開啟網站就能用的樣子。

**第一次啟用前請先確認：**
1. 要用系統的每個人，都已在「人員管理」建立好，並設定了員工編號和打卡密碼。
2. 在「使用者權限管理」替每個人指定好分類。
3. 管理員至少 1～2 位，才進得去設定。

## 登錄後馬上打卡、電腦與平板左側分類（版本 2026.10.02-f）

**登錄後馬上打卡**
- 員工用員工編號登錄後，系統會自動跳出「歡迎 ○○○」：平日上班時間內還沒打上班卡，就提示「上班打卡」；過了下班時間還沒打下班卡，就提示「下班打卡」。一個按鈕就打卡，不用再輸入員工編號和密碼。
- 首頁最上面有「上下班打卡」卡片，顯示今天的上班、下班時間，兩顆大按鈕，下一步該按的那顆會反白。
- 「更多 → 人事與考核 → 上下班打卡」，登錄後會直接進入打卡畫面。
- 打卡時系統會自動拍照並記錄位置（瀏覽器第一次會問是否允許）。今天已經打過上班卡再按，會先確認。

**電腦與 iPad 左側的分類**
- 電腦和 iPad 的左側欄，改成和「更多」頁面相同的十個分類：銷售與訂單、採購與進貨、庫存與商品、配送與車輛、收款與帳務、票據與現金、客戶與供應商、人事與考核、報表與稽核、系統與設定；上面是「首頁」，最下面是「全部功能」。
- 點左側的分類，右邊就是「更多」頁面，那一類已經展開。沒有權限的分類不會顯示。
- 原本的「庫存／訂購／單據／帳款」四個按鈕不在左側了，改從分類進去：單據清單在「銷售與訂單 → 單據查詢」，其他在各分類的第一項附近。
- 手機版的底部列不變。

## 資料用量上限（版本 2026.10.02-g）

- 網站版（這個資料夾）**沒有文件數量上限**：系統設定裡顯示「已使用 N 份文件 / 無上限」，匯入資料也不再被擋。
- 真正的用量上限來自 **Firebase 的方案**。免費的 Spark 方案每天有讀寫次數上限（超過會暫停，隔天重置），儲存空間也有上限。
- 要取消每天的次數限制，把 Firebase 升級成 **Blaze（依用量計費）**：Firebase 主控台 → 左下角「Spark 免費」→ **升級** → 選 Blaze → 綁定付款方式（信用卡）。Blaze 仍保留每月免費額度，超過才計費，小公司通常很低。
- 升級後務必到 Google Cloud 主控台 → **帳單 → 預算與快訊**，設一個每月預算（例如 NT$300），到 50%、90%、100% 時寄信通知你。預算只是通知，不會自動停用。
- 如果免費額度用完，畫面會顯示「資料庫今天的免費用量用完了…」，提醒管理員升級或等隔天。
- Claude 裡的版本，用量上限由 Claude 平台決定，系統沒辦法取消。

## 產品照片與包裝照片（版本 2026.10.02-h）

- 產品資料有兩種照片：**產品照片**（商品本身）和**包裝照片**（外箱、包裝袋、標籤）。在「庫存 → 點商品 → 編輯」，各有自己的「拍照」「選取檔案」和「移除」。

## 打卡照片大小上限（版本 2026.10.02-m）

## 循環盤點（版本 2026.10.02-ah）

「更多 → 庫存與商品 → **循環盤點**」；首頁也有「今天的循環盤點」卡片。取代每月一次的人工目視全面盤點：系統每天排出最值得盤的商品，同仁用掃碼槍或手機掃條碼盤，盤完自動算差異、產生盤點調整單。

**怎麼決定盤哪些（風險評分，用你自己的資料算，每一項都有原因，不是語言模型猜的）**
- 重要程度（ABC）：賣得最好、占 70% 銷售金額的是 A 類；接著 20% 是 B 類；其餘 C 類。沒賣出但庫存金額很高的商品算 B 類。預設 A 類每 14 天、B 類每 30 天、C 類每 90 天盤一次（可改）。
- 自動學習：上次盤點有差異的商品，盤點週期縮短一半；連續幾次都吻合的商品，週期拉長（最多 2 倍）。
- 評分項目（滿分 100）：多久沒盤（30）、帳面異常（20，包含庫存為負、帳面 0 但最近有出貨、最近大量手動調整、剛有退貨）、上次盤點有沒有差異（20）、上次盤點後動了幾次（15，沒動過的商品出錯機會小）、庫存金額（15）。A 類逾期另外加分。
- 一定會排進去：庫存為負、帳面 0 但最近有出貨、A 類從來沒盤過。盤完確認過、之後沒有異動的商品，不會因為「最近的事」重複盤。剛盤過幾天內、沒有異常的商品先不重複盤。完全沒庫存也沒動過的呆品不列入。
- 每天最多盤幾項（預設 30，可改），依分數取最高的，再**依架位排序**，順著走不繞路；沒有架位的排最後。超過的會告訴你「還有 N 項」，明天接著排。

**盤點流程**
1. 看「今日清單」：每項有架位、類別、原因（例如「已 20 天沒盤（A 類每 7 天）」「上次差 -3」「庫存為負」）。可以按「今天不盤」去掉某項，或「手動加入商品」。
2. 按「開始今天的循環盤點」：建立一個只涵蓋這份清單的盤點（預設盲盤，不顯示帳面數量），接著用原本的掃碼盤點畫面。
3. 「檢視差異並完成」：沒盤到的不會調整，會留在之後的清單；差異大的標紅字「建議複盤」。確認後自動建立盤點調整單。

**成效頁**：各類別盤點涵蓋率、90 天內盤過幾項、最近幾次循環盤點的帳實吻合率與盤虧金額、和每月全面盤點相比省下多少工夫。
**設定頁**（管理員）：每天幾項、A／B／C 週期、預設盲盤、盤點哪個倉庫。

## 打卡防呆：位置檢查、伺服器時間、異常打卡由主管確認（版本 2026.10.02-am）

**這次要換的檔案**：`index.html`、`firebase-boot.js`、`firebase-adapter.js`（三個一起傳到 GitHub）。雲端函式和資料庫規則沒有變。

**原本就有的**：打卡時自動拍照（用相機即時拍，不能從相簿選）、記錄位置、員工代號加密碼、首頁的上班打卡鍵只在上班前後 30 分鐘內出現。
**原本的漏洞**：位置只有「記錄」，沒有判斷在不在公司；打卡時間用的是**手機自己的時鐘**，改手機時間就能假裝準時。

**1. 公司位置檢查**（「更多 → 人事與考核 → 考勤管理 → 設定 → 打卡位置檢查」，管理員）
- 人站在公司裡，按「用我現在的位置新增公司地點」，取名字；範圍預設 150 公尺，可以改（30～3000）。可以設多個地點（總公司、倉庫…），在任何一個範圍內都算到公司。定位誤差大於 100 公尺（可改）時不能新增。
- **沒有設定任何地點時，完全不檢查**，不會因為還沒設好就把人擋在外面。
- 內勤人員不在範圍內時，三種處理方式：**不檢查**、**照常打卡但要主管確認**（預設）、**直接擋下不能打卡**。外勤人員（出差、跑客戶）預設不檢查，也可以設成距離公司太遠才要確認。
- 建議先用「照常打卡但要主管確認」跑一兩週，看看範圍設得合不合理，再改成「直接擋下」。
- 判斷方式：算打卡位置到最近地點的距離，扣掉定位誤差（最多扣到上限，對誠實的人有利）後，在範圍內就算到公司。定位誤差比上限大（例如 150 公尺），算「定位不準」，不能信。
- 每次打卡都強制取新的定位，不使用手機存的舊位置。

**2. 打卡時間改用伺服器時間**
- 打卡時，系統先問資料庫伺服器現在幾點，**用伺服器的時間當打卡時間**，不再用手機的時鐘。改手機時間沒有用。
- 手機時間和伺服器差 3 分鐘以上（可改），這筆打卡會標記「手機時間差 ○ 分鐘（已改用標準時間）」，列入主管確認。
- 連不上伺服器（例如沒有網路）時，改用手機時間，標記「沒有連上伺服器，時間沒有校對」，列入主管確認。

**3. 異常打卡由主管確認**
- 「不在公司範圍」「沒有位置」「定位不準」「手機時間不準」「沒連上伺服器」的打卡，會照常記錄（擋下模式除外），但標成**待確認**。
- 首頁（有考勤管理權限的人）出現「打卡待確認 ○ 筆」；「考勤管理」多了「打卡待確認」分頁，每筆顯示原因、打卡照片、地圖連結，按「確認有效」或「不採計」（要寫原因）。
- 待確認的那天，在考勤統計裡顯示「待確認」，不是「正常」。**確認有效**後照常算出勤；**不採計**就當作沒打這一筆，員工可以重新打卡。判定會記在「確認紀錄」裡，不會讓那天的紀錄顯示成「被修改過」。
- 每筆打卡的單日明細頁也會顯示原因和狀態，有權限的人可以在那裡確認。
- 打卡的人看到的結果畫面，會寫明為什麼要確認（例如「不在公司範圍（距離「總公司」約 3.2 公里）」「已記錄，等主管確認」）。擋下模式會跳出說明，並且不記錄這次打卡。

**做不到的、要注意的**
- **手機的定位可以被「假 GPS」軟體騙過**，網頁偵測不到。所以位置檢查不能保證人一定在公司。要搭配打卡照片（主管看照片是不是本人、背景是不是公司）和抽查。
- 這個系統沒有做人臉辨識（涉及個資和誤判），照片要靠人看。
- 「別人拿你的代號和密碼代打卡」，靠照片抓；員工代號和密碼要自己保管。
- 有改打卡時間、補打卡權限的人，原本就會留下修改紀錄。
- 打卡位置、照片屬於員工個資，要在僱用時告知並取得同意。
- 這次**沒有做**「綁定員工的手機（只能用自己的裝置打卡）」，因為公司若有共用的打卡平板就會互相衝突；需要的話，之後可以加。

## 鍵盤輸入最佳化（版本 2026.10.02-ap）

整個操作介面共用的鍵盤功能（滑鼠、手機觸控照常能用）。說明頁在「更多 → 系統與設定 → 鍵盤快速鍵」，沒有視窗、也沒有在打字時按 `?` 也會打開。

**輸入資料（所有輸入視窗）**
- **Enter**：到下一格。**最後一格按 Enter 只會停在「儲存」鈕上，再按一次 Enter 才會儲存**，不會手滑存檔。
- **Ctrl + Enter** 或 **Ctrl + S**（Mac 用 ⌘）：不管游標在哪一格（包含「搜尋商品」格）都直接儲存；Ctrl + S 也會擋掉瀏覽器的「另存網頁」。
- **Shift + Tab**：上一格。**Tab** 在視窗裡循環，不會跑到視窗後面的頁面。
- **Esc**：關閉視窗；在搜尋框裡先清掉搜尋文字，再按一次才關視窗。
- **用中文輸入法選字時按 Enter，只會確認選字，不會跳到下一格**（包含舊版瀏覽器）。
- 電腦版開啟視窗時，游標會自動停在第一格（手機不會，避免突然跳出鍵盤）；數字格點進去會整格選取，直接打字就會取代；手機的鍵盤會顯示「下一個」鍵。
- 視窗底下（電腦版）有一行小字提示這些按鍵。

## 價格策略：組合優惠與買送贈品（版本 2026.10.02-aq）

「價格策略」頁（系統設定 → 價格等級與折扣 → 價格策略）原本是「單一商品」的規則（客戶等級價、數量階梯價、促銷期間價…）。這次多了第二區「**組合優惠與買送贈品**」，處理兩樣以上商品合買、和買到一定數量就送贈品。按下方「組合／買送」新增。

**組合優惠**（兩樣以上商品，買到一定數量就有優惠價）
- **任選**：這幾樣商品的數量**合計**達到就有優惠。例：水管、接頭任選合計 10 件，單價 9 折。可以再要求「至少要買到幾種不同的商品」（例：至少 2 種，只買 10 件水管不算）。
- **套裝**：每一樣商品都要買到各自的數量。例：水管至少 2、膠帶至少 3。
- **優惠方式**：折數（90 ＝ 9 折）、每件減多少元、或每一樣商品各自指定單價（只有套裝常用）。
- 達到條件時，組合裡每一樣商品的單價都照優惠算；算在「目前的單價」上（已經套了客戶等級價或上次成交價的，就在那個價格上再算）。**優惠不會讓單價變高。**
- 同一個商品同時符合好幾個組合優惠時，取**單價最低**的那一個。
- **手動改過單價的那一行不會被改**，但它的數量仍然算進組合的條件裡。

**買送贈品**
- **買什麼**：指定商品（可多樣，數量合計），或某個商品分類。**買幾件以上**。
- **送什麼**：一個商品、送幾件。贈品可以是同一個商品（買 10 送 1），也可以是別的（管材滿 20 送手套）。
- 勾「每滿一次就再送一次」：買 10 送 1，買 25 件就送 2；不勾就只送一次。可以設「最多送幾件」。
- 贈品會自動加到訂單**最下面**，是**獨立的一行**（不會併進買的那一行，即使是同一個商品）：名稱後面標「（贈品）」、單價 0、庫存照常扣、成本照算（所以贈品的成本會反映在毛利）。訂單合計只算買的商品。
- 開單時按贈品那一行的「不送」就取消這一次，單上會顯示「已取消 1 個贈品」和「恢復」鈕。
- 買的商品被移除、或數量減少到不夠時，贈品會跟著消失或減少。

**共同的設定**：適用對象（全部客戶／某個客戶等級／指定客戶）、期間起迄（含頭尾兩天）、優先順序、停用開關、備註。

**開單時的提示**：還沒達到條件時，單子下面會提示「再買 8 件（水管、接頭 任選），就有「水管接頭任選10件9折」…」「再買 1 件，送 礦泉水 1」。達到條件、價格自動改變時，那一行會寫明「組合優惠「…」：單價 NT$100 → NT$90」。已儲存的單據，每一行也記著套了哪個方案、原本的單價。

**這次的限制，請注意**
- 目前只用在「**銷貨作業**」開新單。**客戶訂單、報價單**還沒有（價格還是照單一商品的規則算）。
- **修改舊的銷貨單不會**自動加贈品或改價（避免改一張早就談好的單時，內容突然變動）；從客戶訂單轉成銷貨單時，贈品也不會從訂單帶過來，在銷貨單上依條件重新計算。
- 同一個商品在一張單上會出現兩行（買的、送的），這是刻意的：這樣單價、成本和庫存都準確。**退貨**時，系統只會自動帶出買的那一行，贈送的那一件要退的話請手動加。
- 贈品成本用商品目前的進價；毛利報表會把贈品的成本算進去。
- 這次只更新 `index.html`；其他檔案、雲端函式和資料庫規則都沒有變。

## 客戶多位聯絡人；信封標籤不印聯絡人（版本 2026.10.02-ar）

**多位聯絡人**（客戶和供應商都一樣）
- 客戶資料的「聯絡人」區（編輯時預設展開），每一位聯絡人一張卡片：**姓名、部門、電話、Email、備註**。「＋ 新增聯絡人」可以加，最多 10 位；每張卡片可以刪除。
- **第一位是主要聯絡人**。其他位按「設為主要」就會和第一位對調。
- 填了部門、電話、Email 或備註但沒填姓名，不能存（會提示第幾位要填姓名）；Email 格式不對也不能存，並指出是誰的。
- **舊資料不用整理**：原本只有「聯絡人」和「聯絡人電話」兩欄的客戶，會自動當成一位主要聯絡人顯示；編輯存檔後才轉成新格式。
- 客戶頁面列出所有聯絡人：電話點一下就能撥打（`tel:`），Email 點一下就能寄信（`mailto:`），備註一併顯示。
- 客戶搜尋也會比對**每一位**聯絡人的姓名、部門、電話、Email。
- 為了不影響原有功能，存檔時系統會把**主要聯絡人**的姓名和電話同步寫回原本的「聯絡人」「聯絡人電話」兩欄；送貨單、客戶清單匯出、搜尋等舊功能照常運作，不需要改。
- **開銷貨單時**，如果客戶有兩位以上聯絡人，送貨資訊那裡多一排「帶入聯絡人：王小姐・採購部／李先生・會計部」，點一下就把那位的姓名和電話帶進送貨聯絡人和送貨電話；預設仍是主要聯絡人。

**匯入／匯出**（更多 → 客戶與供應商 → 資料匯入匯出）
- 客戶資料多一欄「**聯絡人明細**」：每一位聯絡人一行（Excel 裡是儲存格內換行），格式是 `姓名|部門|電話|Email|備註`，例如 `李先生|會計部|02-2222-3333#12|lee@datong.com|對帳找他`。
- 匯入時也可以用「；」分開多位聯絡人；每位至少要有姓名（欄位可以只寫姓名）。Email 格式不對會提醒並略過那個 Email，其他資料照收。
- 原本的「聯絡人」「聯絡人電話」兩欄還在，匯出的內容是主要聯絡人。**舊格式的檔案（只有這兩欄）仍然能匯入**，而且只會更新主要聯絡人的姓名和電話，不會動他的部門、Email，也不會動其他聯絡人。
- 檔案裡「聯絡人明細」是空白的，不會清掉已經存的聯絡人；有填的話，會用檔案的內容**整批取代**這位客戶的聯絡人。
- 匯出再匯入，內容不變（有測試）。下載的匯入範本也有範例。

**信封標籤不印聯絡人**
- 「應收帳款明細」每位客戶那一頁最上方的標籤，和獨立的「信封標籤（橫式）」，收件人現在只印「**客戶名稱　收**」；不印任何聯絡人的姓名、電話或 Email。寄件人、郵遞區號和地址照舊。
- **送貨單**上的「聯絡人」不受影響（那是這張單的送貨聯絡人，用來讓司機聯絡收貨的人）。

## 暫停往來（版本 2026.10.02-as）

客戶和供應商的資料，「聯絡人」區最上面多了一個核取方塊「**暫停往來**」，打勾後出現「**暫停日期**」（預設今天，可以改成別天）。取消打勾就恢復往來，日期清掉。

> **這是記在「客戶（或供應商）」身上，不是記在某一位聯絡人身上。** 只是放在「聯絡人」區，方便你在同一個地方看到。如果你要的是「某一位聯絡人離職、不再聯絡」，那是另一件事，請告訴我，我可以另外加。

**暫停之後會怎樣**
- 客戶頁面「往來狀態」一列用紅字寫「暫停往來（自 2026-09-20 起）」；客戶管理清單的名字後面有紅色「暫停往來」標示，上面多一個「暫停往來」篩選（有人暫停時才出現）。
- 選客戶時（銷貨、客戶訂單、報價…所有用客戶挑選器的地方），客戶名稱下面會用紅字寫出暫停的日期。
- **新開**以下單據時，會先跳出提醒：「這位往來對象已暫停往來。「○○」暫停往來（自 … 起）。仍要開這張○○嗎？」，由開單的人決定「取消」或「仍要繼續」：銷貨單、進貨單（供應商）、客戶訂單、採購單、報價單、報價單轉客戶訂單、LINE 訂單核准。
- **不會擋**的：收款、對帳、應收帳款報表、LINE 對帳與逾期提醒（客戶欠的帳還是要收）、退貨登記與處理、修改或作廢舊單據、LINE 訂單的駁回。
- 提醒只有「提醒一次」，不是禁止；要真的擋住，請在客戶那邊不要讓人開單，或告訴我，我可以加一個「暫停往來的客戶一律不能開單」的選項。

**日期的意思**
- 暫停日期**當天起**才開始提醒；日期是未來的，只算「預計」（清單顯示「預計暫停」、頁面寫「預計 2026-12-01 起暫停往來」，顏色是橘色，不提醒），到了那天自動生效。
- 打勾但沒有日期（例如舊資料），視為已暫停。

**匯入／匯出**
- 客戶匯出多了兩欄：「暫停往來」（是／空白）和「暫停日期」。匯出再匯入，內容不變。
- 匯入：暫停往來寫「是」就是暫停（沒寫日期就用今天），寫「否」就恢復（並清掉日期）；日期可以寫 2026-10-05 或 2026/10/5；寫不是「是／否」的字，或日期格式不對，會警告並略過，不會亂猜；只有日期、沒有打勾的客戶，日期會被略過並警告；檔案裡沒有這兩欄，就完全不會動這個設定（空白不會覆蓋原本的設定）。

**限制**：沒有留下「什麼時候恢復往來」的紀錄——取消打勾就是清掉日期。若要保留暫停過的歷史，請在客戶備註寫一筆。

## 修正：iPhone 相機即時掃描（版本 2026.10.02-at）

**問題**：在 iPhone（例如 iPhone 11 Pro Max）按「相機掃描」（揀貨、盤點、掃 QR Code 等所有用到相機掃描的地方），會跳出「這個裝置不支援相機即時掃描，請改用「拍照」或掃碼槍」。

**修正**：瀏覽器有內建偵測就照舊用；**沒有的（iPhone）就改用 ZXing 自己讀相機畫面**，每秒約 4 次。支援商品常見的條碼：EAN-13、EAN-8、UPC-A、UPC-E、Code 128、Code 39、Code 93、ITF、Codabar，以及 QR Code、Data Matrix。相機也改成要求較高的解析度（1280×720），讀一維條碼比較準。
- 第一次按會先顯示「掃描程式載入中…」一兩秒（要從網路下載 ZXing，約 100 KB，之後瀏覽器會暫存）；**要連上網路**。載入失敗會關閉相機並說明，可以改用「拍照」或掃碼槍。
- 同一個條碼 1.8 秒內不會重複算兩次（原本的設計沒變）。
- 相機畫面不會被全螢幕接管（iPhone 需要 playsinline），影片也設成靜音自動播放。

**仍然要注意的**
- 第一次使用，iPhone 會問「要允許使用相機嗎」，請按允許；如果之前按了不允許，要到「設定 → Safari → 相機」或「設定 → 隱私權與安全性 → 相機」改回來。
- **如果是在 Claude 的 App 或 Claude 網頁裡（成品預覽）開這個系統，相機可能會被擋住**（那是 Claude 的沙盒限制，不是程式的問題），這時會跳出「無法開啟相機，請允許相機權限，或改用「拍照」」。請用 GitHub 上的**正式網站**（Safari 直接開網址，最好用「加入主畫面」）。
- 光線太暗、條碼太小或有反光時，即時掃描比專用的掃碼槍慢，對準一點、拿遠一點（約 15～25 公分）、等一秒；還是讀不到就改用「拍照」。

## 清除所有資料（版本 2026.10.02-au）

「更多 → 系統與設定 → **清除所有資料**」（只有管理員）。用來在正式上線前清掉測試資料，或不再使用時把資料刪乾淨。**刪掉就拿不回來，只能用備份檔還原。**

**兩種範圍**
- **只清交易資料**：刪銷貨、進貨、調整、客戶訂單、採購單、報價單、收款付款、票據、盤點、退貨、考勤打卡、請假、薪資、LINE 訂單、出車、費用單據，以及這些單據的照片。**留**：商品、客戶、供應商、價格規則、組合優惠、車輛、人員、系統設定、登入帳號和權限。庫存會變成 0（庫存是由單據算出來的）。**單據流水號保留**，新開的單據接續編號，不會重複。
- **全部清除**：上面全部，再加商品、客戶（含聯絡人）、供應商、價格規則、組合優惠、車輛、油卡、人員、發票與單據格式設定、備份設定、**單據流水號**。系統回到空白。**只留**登入帳號、成員和角色權限（不然你會被鎖在外面）、以及「是否要登入」的設定。

**四道關卡，缺一不可（按鈕才會亮）**
1. 按「計算會刪除多少資料（還不會刪）」：先看到每一類要刪幾筆、合計幾筆。這一步不會刪任何東西。
2. **下載備份檔**，並勾選「我已經確認備份檔存好了，而且打得開」。每清除一次，這個勾選就會被取消，下一次要重新確認。
3. 完整輸入確認字：只清交易資料要輸入「清除交易資料」，全部清除要輸入「刪除全部資料」（前後空白不算；輸入另一個範圍的字不行）。換範圍時，計算結果和確認字都會清掉。
4. 按「永久刪除」後，還有一個最後確認視窗（預設停在「取消」，按 Enter 不會刪）。

**清除時**：畫面顯示進度；可以按「中止」，會在目前這一批做完後停下，沒刪的還在。每一筆資料各自記成功或失敗，**失敗的不會被當成成功**：結果寫「刪除 ○ 筆，失敗 ○ 筆（哪一類）」。清除紀錄（時間、範圍、筆數、操作的人）寫在系統設定裡，頁面上方顯示「上次清除」。

**這個功能清不掉的（要另外處理）**
1. **沒有任何單據指向的孤立照片**：照片放在另外的集合，系統是用「單據記著的照片代號」去刪；沒有單據指向的照片（例如單據早就被刪掉的）找不到，不會被刪。要清乾淨，請用下面第 6 項。
2. **雲端自動備份檔**（Firebase 主控台 → Storage → `backups`，保留最近 35 天、每月 1 號的留一年）：要到 Storage 手動刪。
3. **登入帳號**（Firebase 主控台 → Authentication）和 Firestore 的 `inv_users`、`inv_members`：刻意保留。要刪的話請在主控台手動刪（刪掉之後就沒有人能登入了）。
4. **LINE 官方帳號裡的聊天紀錄**：在 LINE Official Account Manager 刪除，或請客人封鎖並刪除對話；LINE 的資料不在這個系統裡。
5. **你已經下載的備份檔和匯出檔**（手機、電腦、雲端硬碟）：自己刪。
6. **Google Cloud 的日誌和 Cloud Functions 的紀錄**：在 Google Cloud 主控台的 Logging 處理。

## 修正：搜尋框可以用注音、倉頡輸入法（版本 2026.10.06-aw）

**原因**：用注音、倉頡打字時，字是「組字中」，要選字、按 Enter 才會定案。系統在這段時間會重畫畫面（「更多」頁的搜尋框每打一個符號就整頁重畫；視窗裡的搜尋框，別人存了資料、或停頓 0.25 秒也會重畫），輸入框被換成新的，組字就被打斷，字打不出來。英文、數字沒有組字，所以不受影響。

**修正**（全系統一次處理，不是一個搜尋框一個搜尋框改）：
1. **組字中不重畫畫面**：資料更新先記下來，組字結束再補畫。
2. **組字中的注音符號、倉頡字根不拿去搜尋**：等選好字再搜，搜尋結果不會在組字時一直閃「找不到」。英數字照舊即時搜尋。
3. **組字中按 Enter、Esc、方向鍵是給輸入法用的**：不會誤觸「按 Enter 加入商品」、「Esc 關視窗」、快速鍵。含 Safari／iPhone 選字確認時送出的 Enter（keyCode 229）。
4. **「更多」頁搜尋框**改成只更新下面的結果，搜尋框本身不動。
5. **視窗（客戶管理、應收帳款報表等）重畫後，游標會回到原本的輸入格**：搜尋打到一半不會因為資料更新而中斷（英文也一樣受益）。

## 新功能：員工打卡可以用臉部辨識（版本 2026.10.06-ax）

員工看著手機（或平板）的鏡頭就能打卡，不用輸入代號和密碼；也可以在輸入代號打卡時，再比對一次臉，防止同事互相代打卡。

### 怎麼用
- **臉部辨識打卡**：「上下班打卡」視窗最上面多一顆大按鈕「臉部辨識打卡」。按下去，看著鏡頭，系統認出是誰就直接打卡（照樣記錄位置、打卡照片、伺服器時間）。認不出來時，下面一樣可以輸入員工代號和密碼。
- **動作驗證（預設開啟）**：為了防止拿照片或影片冒用，系統會隨機要求做一個動作：眨眼、張嘴，或把頭轉向畫面的左／右邊。
- **用代號打卡時也比對臉**：員工已登錄臉部、改用「員工代號＋密碼」打卡時，可以選：不比對／要比對，不符要主管確認／要比對，不符就擋下。（打卡明細會多一行「臉部比對 ✓（差異 0.21）」之類的記錄。）
- 沒登錄臉部的員工完全不受影響，照舊用代號和密碼。
- **相機壞掉、程式載入失敗不會擋人**：只會標記成「待主管確認」，不會讓員工打不了卡。

### 設定步驟（照順序）
1. **更新資料庫規則**：把 `firestore.rules`（或 `firestore.rules.full`）貼到 Firebase 主控台 → Firestore → 規則 → 發布。這次新增了 `inv_faces`（臉部特徵）的規則：可編輯以上能讀（打卡的裝置要拿來比對）、**只有管理員能新增、修改、刪除**。沒更新的話功能仍可用，但「可編輯」的人也能改別人的臉部資料，不建議。
2. **更新網站**：換掉 `index.html`。另外把新的 **`vendor` 和 `models` 兩個資料夾**也放到同一個地方（GitHub 網頁的 Add file → Upload files，可以直接把整個資料夾拖進去；最大的檔案 6.4 MB，沒問題）。**沒放也能用**：系統會自動改從網路（jsDelivr）下載辨識程式和模型，只是第一次比較慢、要有網路；放在自己的網站比較穩，也不依賴外部網站。
3. **開啟功能**：「更多 → 考勤管理 → 設定」最下面有「臉部辨識打卡」，按「開啟」。
4. **替員工登錄臉部**：「人員」→ 點員工 → 最下面「臉部辨識」→「登錄臉部」。要先向員工說明並取得同意（畫面上要勾選「已取得員工同意」才能開始），然後在光線充足的地方拍 5 張，約 15 秒。登錄完可按「測試比對」確認本人過得了。
5. **先用試行模式**：「用代號打卡時」先選「要比對，不符要主管確認」跑一兩週，到考勤明細看每個人的比對差異值（本人通常很小），確定沒問題再改成「不符就擋下」。

### 隱私
- **只存臉部特徵（一串 128 個數字，登錄 5 張就是 5 串），不存臉部照片。** 打卡照片是原本就有的功能，沒有改變。
- 登錄前必須勾選員工已同意；記錄是誰、什麼時候登錄的。
- 比對是在員工自己的手機裡進行的，臉部影像不會傳到任何伺服器（辨識程式與模型是從你的網站載入的）。
- **員工離職時，請到「人員 → 臉部辨識 → 刪除臉部資料」**，系統不會自動刪。

### 比對的嚴格度怎麼調
設定裡有三段：寬鬆 0.50、標準 0.45（預設）、嚴格 0.40，數字是「臉部特徵的差異」，越小越像。系統另外要求：臉部辨識打卡時，最像的人要比第二像的人明顯更像（差 0.07 以上），否則視為「分不出是誰」，請改用代號。
- 我用 6 張真人合照測過：**不同人之間的差異最小約 0.48**，所以 0.45 偏保守（寧可請本人再試一次，也不要認錯人）。
- 但這只是照片。真正的數字要看你們員工在打卡現場的結果：每次打卡都記下差異值，請看一兩週的明細再調整。**兄弟姊妹、長得很像的同事，可能需要用「嚴格 0.40」，或乾脆不要用臉部辨識打卡、只用「代號打卡時比對」。**

### 這個功能擋得住什麼、擋不住什麼
- 擋得住：同事用你的代號和密碼幫你打卡（臉不符）、拿你的照片或影片對著鏡頭（動作驗證）。

### 驗證
- 新增 202 項自動測試（辨識判斷與動作驗證 52、打卡全流程 98、其他）、再加上輸入法 51 項、以及先前累積的回歸測試，全部通過。

  1. **沒有用真人的臉驗證眨眼、張嘴、轉頭**：我這裡沒有真人影片。眨眼的判定用的是眼睛開合度，張嘴和轉頭的門檻是用真人照片的數值訂的，但眨眼我沒有真人閉眼的資料可以驗證。**請找一位員工，用 iPhone 和 Android 各試幾次**（「人員 → 臉部辨識 → 測試比對」會走一樣的流程）；如果某個動作一直過不了，告訴我是哪一個，我來調整。

| 商品範圍、商品內容 | 全部／商品分類／商品系列／指定商品（內容填**料號**，也可填條碼或不重複的品名） |
| 計價方式 | 折數（%）／折讓金額／固定單價／成本加成（%） |
| 數值 | 折數可以寫 `9折`、`90%`、`0.9`、`90`，都是 9 折；單獨寫 `9` 也當 9 折並在預覽提醒。其他計價方式填金額或百分比 |
| 數量從、數量到 | 數量階梯。**空白＝沒有限制** |
| 合併同系列數量 | 是／否 |
| 期間起、期間迄 | 日期，可以寫 2026-10-07、2026/10/7、民國 115/10/7、20261007。**空白＝一直有效** |
| 促銷價、優先順序、啟用、備註 | 空白＝更新時沿用原本的；新增時用預設值（優先順序和「價格等級與折扣」的算法一樣） |

### 組合優惠與買送的欄位
- 類型填「組合優惠」或「買送贈品」。
- **組合優惠**：組合方式（任選／套裝）、組合商品（寫成 `料號*至少數量@優惠單價`，用「、」分隔，例如 `T-RED*2@85、MUG*1@40`）、合計數量、至少幾種、優惠方式（折數／每件減多少元／每樣商品指定單價）、優惠數值。

- 沒填方案編號時，用「類型＋名稱」找原本的方案；有兩個以上同名會請你填編號。

### 三種匯入方式
- **新增，並更新已存在的**（預設）
- **只新增，已存在的略過**
- **完全依檔案取代（檔案裡沒有的會刪除）**：⚠️ 會刪除不在檔案裡的規則。保護措施：檔案有任何錯誤列就不能用這個方式；刪除前有確認視窗寫明要刪幾條、無法復原；視窗裡有「先匯出目前的資料」可以先備份。

## 新功能：銷貨單開立後，用 LINE 通知客戶出貨的商品和數量（版本 2026.10.07-az）

客戶訂單轉成銷貨單、存檔後，系統自動用 LINE 傳一則「出貨內容」給客戶，例如：

```
【承益企業】甲您好，您訂購的商品已開立銷貨單 S1006-001（10/6（二）），出貨內容如下：
・T恤 紅 ×10 件
・馬克杯 ×3 個（訂購 5，尚欠 2）
共 2 項。
尚未出貨：T恤 藍 ×6 件
如與您的訂單不符，請與我們聯絡，謝謝。
```

- **每個品項一行、數量和單位都列出來**；品項再多也不會悄悄少掉（太長超過 LINE 上限時，會寫「另有幾項」）。
- **和訂單比對**：這次少出的品項註明「訂購幾、尚欠幾」；訂單裡這次完全沒出的品項列在「尚未出貨」。分批出貨時，前面已經出過的會扣掉；已作廢的銷貨單不算已出。贈品照列，不算欠貨。
- **預設不含金額**；要放金額，在訊息範本加 `{金額}`。

### 誰會收到（條件要同時成立）
1. 「LINE 通知設定」已啟用；
2. 客戶已綁定 LINE（沒綁定的不會通知）；
3. 設定裡「銷貨單開立後 → 通知客戶出貨的商品和數量」有勾（預設勾起）；
4. 預設只通知**從客戶訂單轉出的**銷貨單。直接開的銷貨單不會自動通知；想要的話，設定裡「哪些銷貨單要通知」改成「所有已綁定 LINE 的客戶的銷貨單」。

### 設定與手動通知
- **更多 → 系統與設定 → LINE 通知設定 → 通知客戶**：開關、範圍、訊息範本。「用最近一張銷貨單預覽這則訊息」可以先看長什麼樣子（只預覽，不會寄出）。可用欄位：`{公司} {客戶} {單號} {訂單單號} {日期} {品項} {品項數} {金額} {未出貨}`。
- **單據詳情**（銷貨單、客戶已綁定 LINE）：多一列「LINE 通知客戶」。按「通知商品數量」會先顯示要傳的內容，確認再寄；寄過之後顯示「已通知 時間」，按鈕變成「再通知一次」。直接開的銷貨單、或修改過數量的銷貨單，都可以用這個重寄。
- 順便修正：LINE 通知設定頁原本每個範本下面的「可用：{公司} {客戶}…」說明文字沒有顯示出來，現在看得到了。

### 要注意
- **每一則都用掉 1 則 LINE 訊息額度**（免費方案每月 200 則）。每開一張從訂單轉出的銷貨單就是 1 則，請依你們的開單量估算；額度用完時，網站首頁會出現「系統提醒」，客人的通知也會失敗。
- **同一張銷貨單自動只通知一次**。事後修改銷貨單的數量，不會自動再通知，客人手上的是修改前的內容——要更正請在單據詳情按「再通知一次」。
- 通知是在**開單當下**傳的，不是出貨當下；配送排車後的「配送通知」是另一則，照舊。
- 是否真的傳到，要看雲端函式（`sendOutbox`）有沒有部署、客戶有沒有封鎖官方帳號。傳失敗時管理者會收到「LINE 訊息沒有送出：○○（銷貨單通知）」。

### 要更新什麼
- **網站：換 `index.html`**（功能都在網站）。
- **雲端函式：不用重新部署也能用**。這則訊息是網站放進發送佇列（`inv_lineoutbox`，既有的），原本的 `sendOutbox` 就會推播。重新部署（`line-functions.zip`）只多一個好處：傳失敗的提醒會寫「銷貨單通知」，不然會顯示 `slip`。
- Firebase 規則不用改。

### 驗證
- 新增 67 項網站自動測試（訊息內容、和訂單比對與分批、品項太多、各種「不該通知」的情況、開單存檔後真的排入發送佇列且不重複、單據詳情的手動通知、設定頁儲存與預覽、舊設定升級），全部通過；其他測試（價格策略匯入匯出 124、臉部辨識 150、輸入法 51…）全部重跑通過。雲端函式測試 68 項（新增 1 項）通過。
- **沒做到的**：沒有用真的 LINE 官方帳號、真的手機實際收過這則訊息（測試只確認「訊息內容正確、排進發送佇列、`sendOutbox` 會原文推播」）。請先用一位自己的客戶（把自己的 LINE 綁在一個測試客戶上）開一張從訂單轉出的銷貨單，看手機收到的樣子，再讓正式客戶開始收。

## 新功能：價格規則可以一次選多個商品（版本 2026.10.11-ba）

新增價格規則時，選好「對象」之後，「商品」選「**指定商品（多選）**」，就可以一次選很多個商品，**存成同一條規則**。

### 怎麼用
1. 更多 → 價格策略（管理價格規則）→ 新增規則。
2. 「對象」選全部、客戶等級或指定對象（可以先選好某位客戶）。
3. 「商品」選「指定商品（多選）」→ 按「＋ 選擇商品（可多選）」。
4. 選商品視窗：可以搜尋品名／料號／條碼、用「分類」篩選、一個一個勾，或按「全選符合的」一次選整批；換搜尋字不會丟掉已經勾的。按「確定」回到表單。
5. 表單裡會列出已選的商品，每一個可以按 ✕ 移除；「增減商品」可以再回去加減。
6. 折數／金額、數量區間、期間都只填一次，這些商品全部套用同樣的設定。

「價格等級與折扣 → 依商品編號的折扣率」的商品欄也一樣可以多選。

### 好處
- 之後要改折數或結束日期，**改這一條就全部一起改**，不用一個商品改一次。
- 一條規則含 120 個商品也只佔一筆資料，不會讓規則清單變很長。
- 規則清單會寫成「馬克杯 等 3 項」。

### 要注意
- 選了多個商品時，**每個商品用同樣的數值**。「固定單價」會讓所有選的商品都是同一個單價（表單會提醒）；各商品單價不同，請分開建立規則，或用「價格策略匯入匯出」一次匯入。
- 只選一個商品時，資料格式和以前完全一樣；**舊的規則不用轉換、照常有效**。
- 已經存成多商品的規則，如果有人還開著舊版網頁，舊版只會認第一個商品。更新網站後請請大家重新整理頁面。
- 清單只列前 100 項（請用搜尋或分類縮小範圍），但「全選符合的」會選到全部符合的，不只是畫面上看得到的。

### 匯入／匯出（Excel／CSV）
- 「商品範圍」是**指定商品**時，「商品內容」可以填多個料號，用「、」分隔，例如 `MUG、T-RED、T-BLUE`（逗號、分號也可以）。
- 匯出時，多商品規則會自動寫成這個格式；匯出再匯入不會被當成有變動。料號順序不同、大小寫不同，也視為同一組商品。
- 其中有任何一個找不到的料號，那一列會整列不匯入，並一次列出所有找不到的料號。
- 成本加成的規則，若選的商品有進價是 0 的，匯入預覽會提醒是哪幾個。
- 下載的匯入範本多了一列「兩個商品」的示範。

### 要更新什麼
- **網站：換 `index.html`**（功能都在網站）。
- Firebase 規則、雲端函式都不用動。

### 驗證
- 新增 78 項自動測試：選商品視窗（搜尋、分類、全選、取消、超過 100 筆）、儲存格式（多個／一個）、開單比對（清單內有折扣、清單外沒有、舊格式規則照常有效）、編輯與移除、已刪除商品、價格等級表單、匯出匯入來回、新增與錯誤訊息、範本。原有的 11 組測試（共 500 多項）全部照常通過。
- 另外用真正的瀏覽器（手機寬度）看過選商品視窗和表單的排版。
- **沒做到的**：沒有在真的 iPhone／Firebase 上操作過。請先建一條含 2～3 個商品的規則，到開銷貨單試一次，看單價有沒有照規則帶入。

## 新功能：客戶訂單、採購單開好之後可以修改（版本 2026.10.11-bb）

以前客戶訂單和採購單開好之後，只能「結案」「作廢」或「轉出貨」，明細打錯就得作廢重開。現在可以直接修改。

### 怎麼用
訂單詳情（客戶訂單、採購單都一樣）→ 明細下方的「**修改**」→ 改好按「儲存修改」。
可以改：數量、單價（折數）、增減品項、訂單日期、交貨日（採購單是預計到貨日）、倉庫、備註；還沒出貨的訂單也可以換客戶。

### 限制（避免改壞帳）
- **只有「待出貨／部分出貨」的訂單能改**。已完成、已結案、已作廢的不能改。
- **已經出過貨的品項**：數量不能低於已出貨的量、不能移除、不能換客戶（採購單同理，看已收貨的量）。畫面上那一行會寫「已出貨 4（數量不能低於這個）」，移除鍵也按不下去。
- **已覆核的訂單不能改**，詳情頁會說明要先「取消覆核」。期間已封存的月份同樣不能改。
- **誰能改**：訂單建立的人，或管理員（和「作廢」的規定一樣）。
- 原本品項的**單價不會因為你改數量而自動變**（不會被數量階梯價改掉你當初談好的價錢）；新加的品項才會自動帶入價格規則。
- 修改時，「已被其他訂單預留」「採購在途」的數字不會把這張訂單自己算進去。

### 修改紀錄
每次修改都會記下：什麼時候、誰改的、改了什麼（例如「T恤 紅 10→8；馬克杯 單價 NT$50→NT$45；新增 T恤 綠 ×3；交貨日 10/8→10/10」）、合計從多少變成多少。在訂單詳情的「修改紀錄」可以看到（保留最近 20 次），詳情頁也會顯示「最後修改」。沒有改任何內容就存檔，不會留下紀錄。

### 要注意
- **修改訂單不會自動用 LINE 通知客戶**。如果客人已經收到「訂單確認」的 LINE 訊息，改完之後他手上的內容還是舊的，請另外聯絡。（需要的話可以加「修改後通知客戶」。）
- 銷貨單原本就能修改（詳情頁的「修改」），這次沒有動。
- 修改訂單後，未出貨量、預留量、採購建議都會跟著新的數量重算。

### 要更新什麼
- **網站：換 `index.html`**（功能都在網站）。Firebase 規則、雲端函式都不用動。

### 驗證
- 新增 54 項自動測試：誰看得到「修改」、帶出原內容、沒改就存檔、實際修改（數量／單價／增刪品項／交貨日／備註）、單價不被階梯價改掉、已出貨的限制（低於已出貨量、移除、換客戶）、已覆核與非建立者被擋、採購單、修改紀錄累加、放棄修改的提醒、已刪除商品的那一行。原有 12 組測試全部照常通過。
- 另外用真正的瀏覽器（手機寬度）看過詳情頁和修改畫面的排版。
- **沒做到的**：沒有在真的 iPhone／Firebase 上操作過。請先拿一張測試用的訂單改一次，再到詳情頁看「修改紀錄」。

## 檢查與修正：組合優惠「任選 N 件以上 ＋ 每樣商品指定單價」（版本 2026.10.11-bc）

### 檢查了什麼
組合優惠 → 組合方式「任選（合計 N 件以上）」→ 優惠方式「每樣商品指定單價」。逐項驗證計算是否正確：

| 項目 | 結果 |
|---|---|
| 合計 9 件 → 沒有優惠；10 件 → 達標 | 正確（9 件時會提示「再買 1 件，就有…指定單價」） |
| 每樣商品用「自己的」指定價（例：紅 80、藍 85、馬克杯 40） | 正確，各算各的 |
| 組合以外的商品（例：綠 T 恤）不算進合計，也不被改價 | 正確 |
| 只買組合裡的某一樣、買滿 N 件 | 正確（該樣用指定價） |
| 同一商品分兩行（6＋4 件） | 正確，合計算 10 件 |
| 贈品行不算進合計 | 正確 |
| 手動改過價格的行 | 數量照算進合計，但**價格不會被改掉**（以你手動輸入的為準） |
| 指定價比目前單價還高 | 不會調高（優惠只降不升）；等於目前價也不動 |
| 「至少幾種不同商品」、期間（含第一天、最後一天）、限客戶等級／指定客戶、停用 | 正確 |
| 兩個組合同時成立 | 同一商品取最低價 |
| 組合只有 1 樣商品 | 不成立（要 2 樣以上） |
| 開銷貨單畫面：改數量 9→10→9，單價跟著套用／還原、每行寫明「組合優惠「…」：單價 NT$100 → NT$80」、存檔金額 | 正確 |
| 同時有「10 件以上單價 90」的一般價格規則 | 取較低價（規則 90 vs 指定價 95 → 90；規則 90 vs 指定價 85 → 85） |

### 發現並修正的問題
**指定價有小數時，會被「單價取整」設定改掉。**
例：指定價 12.5，預設的「四捨五入到整數」會變成 13；設成「無條件捨去」會變成 12。
「單價取整」原本是給「打幾折、折讓多少、成本加成」算出來的價格用的，**「指定單價」本來就是你指定的價格，不應該被改**。
現在：指定單價一律照你輸入的（最多 2 位小數）。這個修正同時套用在：
- 組合優惠的「每樣商品指定單價」

「打幾折」「折讓多少」「成本加成」算出來的價格，**仍然依「單價取整」設定**，沒有變。

## 新功能：客戶訂單也會自動套用「組合優惠」（版本 2026.10.11-bd）

以前組合優惠（例如「任選 12 件以上，每件 130」）只有開銷貨單才會自動套用，客戶訂單要自己手動改單價。現在**新增客戶訂單時**也會自動套用。

### 怎麼運作
- 新增客戶訂單 → 選客戶 → 加商品、輸入數量。合計達到組合優惠的件數時，單價**自動變成指定價**，每一行下面會寫「組合優惠「605」：單價 NT$150 → NT$130」，折數欄也跟著變。
- 還差幾件時，明細下面會提示「再買 1 件（…任選），就有「605」指定單價」。
- 數量減少、換客戶、改訂單日期，單價會自動還原（回到原本帶入的價格，例如上次成交價）。
- **手動改過單價的那一行**：數量照算進合計，但單價不會被優惠改掉。
- 訂單存檔後，詳情頁的單價旁邊會寫「組合優惠「605」（原價 NT$150）」。
- 客戶訂單轉成銷貨單時，沿用訂單上的單價（130）。

### 規則和開銷貨單完全一樣
任選／各買幾件、至少幾種、優惠期間、限客戶等級或指定客戶、停用、兩個組合同時成立取最低價、指定價比目前單價高時不調高。

### 不會自動套用的情況（刻意的）
- **修改既有的訂單**：不會自動改單價，保留當初談好的價錢。要改請自己改單價；改了單價的那一行，詳情頁的「組合優惠」標記會拿掉。
- **採購單**：不適用。
- **買送（贈品）優惠**：訂單不會加贈品，轉成銷貨單時才會依數量自動送。
- **報價單、LINE 客人傳來的訂單**：這次沒有動，還是不會自動套用組合優惠。

### 要更新什麼
- **網站：換 `index.html`**。Firebase 規則、雲端函式都不用動。（訂單明細多存了一個 `promo` 欄位，現有規則都允許。）

### 驗證
- 新增 48 項自動測試：加品項、改數量、9 件 → 10 件 → 9 件的套用與還原、手動單價、客戶等級限定、優惠期間（含第一天和過期）、上次成交價 → 優惠 → 還原回上次成交價、存檔內容、詳情頁文字、轉銷貨單單價、修改既有訂單不動單價、採購單不受影響，以及用「台北日新」的真實資料（S-605 牙色 8 ＋ 白色 4 → 130 / 130；牙色 8 ＋ 白色 3 → 150，提示再買 1 件）。其餘 15 組既有測試全部通過。
- 另外用真正的瀏覽器（手機寬度）看過排版。
- **沒做到的**：沒有在真的 iPhone／Firebase 上操作過。

## 新功能：價格規則指定多個商品時，可以各自指定固定單價（版本 2026.10.11-be）

以前一條價格規則選了多個商品、計價方式是「固定單價」時，所有商品都是同一個價格；各商品價格不同就要分開建很多條規則。現在同一條規則裡，每個商品可以有自己的固定單價。

### 怎麼用
系統設定 → 價格策略 → 新增價格規則 → 商品選「指定商品（多選）」→ 選 2 個以上的商品 → 計價方式選「固定單價」→ 勾選「**各商品分別指定價格**」。
勾選後，「已選商品」清單裡每個商品旁邊會出現一個**單價欄**（旁邊也寫著標準價方便對照）。一開始會先帶入上面填的價格，再各自修改。每個商品都要填，沒填不能儲存。
- 之後增減商品：新加的商品單價是空的，要自己填；移除的商品，它的單價也一起拿掉。
- 取消勾選：回到「所有商品同一個單價」，「數值」欄會帶出各商品中最低的那個價格。
- 計價方式不是「固定單價」、或只選 1 個商品時，這個選項不會出現。

### 開單時
- 銷貨單、客戶訂單、價格試算都會依商品帶出各自的價格，並寫明「套用「規則名稱」NT$85」（寫的是這個商品的價格）。
- 其他條件（客戶、數量區間、期間、優先順序、合併同系列）整條規則共用，和以前一樣。
- 指定單價有小數也照指定（不被「單價取整」改掉）。

### 價格策略匯入／匯出
- 匯出：「商品內容」會寫成「**料號@單價**」，用「、」分隔，例如 `T-RED@80、T-BLUE@85`。「數值」欄放各商品中最低的單價（參考用）。
- 匯入：同樣寫法即可新增或修改。計價方式要是「固定單價」；「數值」可以空白（填了但和商品內容不一致時，會警告並以商品內容為準）。
- 每個料號後面都要寫 `@單價`；只有 1 個商品、單價不是數字、料號重複或找不到，都會在預覽時指出是第幾列。
- 舊的寫法（`T-RED、T-BLUE` ＋「數值」）照舊可用，代表同一個價格。
- 匯出後再匯入同一個檔案，不會有任何變動；商品順序不同、價格相同也視為沒變。

### 注意
- 「價格等級與折扣」裡那個只有一個價格欄的小表單，遇到各商品價格不同的規則時，會改開完整的「編輯價格規則」表單，避免存檔時被改成同一個價格。
- 舊規則、舊版匯出的檔案都不用轉換。

### 要更新什麼
- **網站：換 `index.html`**。Firebase 規則、雲端函式都不用動。（規則多存一個 `prod.prices` 欄位，現有規則都允許。）

### 驗證
- 新增 64 項自動測試：計價（各商品價格、舊規則、沒填價格的商品、小數與取整、數量區間、折數規則忽略價格、取最低價／取第一條）、表單（出現與隱藏、單價欄、驗證、新增／編輯／增減商品／取消勾選、儲存內容）、規則清單與價格試算的顯示、匯出匯入（寫法、改價偵測、順序不同、警告與 7 種錯誤、全形＠）、開銷貨單文字、等級小表單的保護。其餘 16 組既有測試全部通過。
- 另外用真正的瀏覽器（手機寬度）看過表單排版。
- **沒做到的**：沒有在真的 iPhone／Firebase 上操作過；「價格等級與折扣」的小表單本身沒有加這個功能（要各商品不同價格請用「價格策略 → 新增價格規則」）。

## 新功能：價格規則、組合優惠的「對象」可以一次勾選多個客戶等級（版本 2026.10.11-bf）

以前一條價格規則的「對象」只能選**一個**客戶等級；要讓「批發」和「VIP」都用同一組價格，就得建兩條一樣的規則。現在同一條規則可以**勾選多個等級**，對應到多個指定商品，計價方式照原本的選單選（折數、折讓金額、固定單價、成本加成；固定單價還可以各商品各自一個價格）。

### 怎麼用
系統設定 → 價格策略 → 新增價格規則 → 「對象」選「**客戶等級**」→ 下面會列出所有等級，每個等級一個勾選框（旁邊寫著這個等級有幾家客戶），勾選要適用的等級 → 「商品」選「指定商品（多選）」→ 選商品 → 選計價方式。
- 一開始會先勾第一個等級；至少要勾一個，沒勾不能儲存。
- 勾選的等級**共用同一個計價方式與數值**（數量區間、期間、優先順序也是共用）。商品是「固定單價」時，仍然可以每個商品各自指定價格。
- 以前存的規則不用轉換：只有一個等級的規則維持原本的格式；多個等級才多存一個等級清單。
- 規則裡的等級後來從等級清單刪掉了，編輯時仍會列出來並標示「已不在等級清單」，不會被悄悄拿掉。
- 組合優惠與買送贈品的「對象」也一樣可以勾選多個等級。

### 開單時
客戶的價格等級（客戶資料裡的等級，沒填就看客戶類別對應的等級）只要在勾選的等級裡，就會套用這條規則／優惠；銷貨單、客戶訂單、價格試算、「再買幾件就有優惠」的提示都一樣。規則清單、價格試算顯示「等級「批發、VIP」」。

### 價格等級與折扣
- 同時適用多個等級的規則，每個等級的畫面裡都看得到，並標示「與「VIP」共用」。
- 點這種規則，會開完整的「編輯價格規則」表單（小表單只能設一個等級，存檔時會把其他等級弄掉）。要新增這種規則，請用畫面下方「全部規則（進階）」。

### 價格策略匯入／匯出
- 匯出：「對象內容」會寫成「**批發、VIP**」（用「、」分隔）；只有一個等級就和以前一樣。
- 匯入：多個等級可以用「、」「,」「;」或換行分隔，大小寫不拘（vip → VIP）。有不存在的等級，那一列不會匯入，並指出是哪個等級；重複的等級只算一個。
- 等級順序不同、內容相同（「批發、VIP」和「VIP、批發」）視為同一條，不會變成重複的新規則，也不算有變動。
- 組合優惠與買送的匯入／匯出一樣。
- 等級名稱本身有「、」時，整串仍可當一個等級（但就不能和別的等級用「、」合併寫）。

### 注意
- 這一版是「勾選的等級共用同一個價格」。如果要**每個等級各自不同的價格**（例如批發 80、VIP 75），目前請各建一條規則；要不要做成「等級 × 商品」的價格表，可以再提。
- 舊資料裡「對象＝客戶等級、但等級空白」的規則，行為不變（只對沒有等級的客戶有效）。

### 要更新什麼
- **網站：換 `index.html`**。Firebase 規則、雲端函式都不用動。

### 驗證
- 新增 100 項自動測試：比對（兩個等級、類別帶出的等級、不在清單裡的等級、舊格式、散客）、四種計價方式、各商品各自單價、數量與期間；表單（勾選、順序、驗證、編輯、存回舊格式、沒有任何等級）；組合優惠表單；「價格等級與折扣」畫面與轉開完整表單；匯出匯入（分隔符號、錯誤訊息、順序不同視為相同、重複內容辨識）；客戶訂單實際帶入單價。其餘 17 組既有測試全部通過。

- 另外用真正的瀏覽器（手機寬度）看過表單與畫面排版。

## 新功能：價格規則可以針對不同商品，各自指定「買幾件以上」的特價（版本 2026.10.11-bg）

以前一條價格規則的數量區間（買幾件以上／到幾件）是整條規則共用的；每個商品的數量門檻、特價不一樣，就得各建一條規則。現在同一條規則裡，**每個商品可以有自己的數量特價階梯**，並且可以和上一版的「多個客戶等級」搭配：多個等級 × 多個指定商品 × 各商品各自的數量特價，計價方式照原本的選單（固定單價、折數、折讓金額、成本加成）。

### 怎麼用
系統設定 → 價格策略 → 新增價格規則 → 「對象」（可勾選多個客戶等級）→ 「商品」選「指定商品（多選）」→ 選商品 → 選「計價方式」→ 勾選「**各商品分別設定數量特價**」。
- 勾選後，每個已選商品下面會有自己的階梯表。每一列填「買幾件以上」「到幾件（選填）」「數值」，按「＋ 新增階梯」多加一列；表格下方會用白話寫出結果，例如「未達 10 件：不適用這條規則；10～29 件 NT$90；30 件起 NT$80」，填完可以對照檢查。
- 例（計價方式＝固定單價）：紅 T 恤「10 件以上 90、30 件以上 80」；藍 T 恤「5 件以上 95」。
- 「數值」依計價方式解讀：固定單價＝每件單價；折數＝折數（寫 90、9、0.9、9折 都是九折）；折讓金額＝每件減多少；成本加成＝加成百分比。想換方式，改上面的「計價方式」，階梯的數值就跟著用新的方式解讀（畫面上會寫明目前的計價方式）。
- 「複製給其他商品」：把這個商品的階梯複製給所有其他已選的商品（會先確認，其他商品原本的階梯會被取代），之後還可以各自修改。
- 只選 1 個商品時，選項會寫成「依購買數量設定特價階梯」；單一商品也可以有好幾個階梯。
- 勾選後，整條規則的「數值」、「數量從／到」、「各商品分別指定價格」不再使用（會隱藏起來）；其他條件（客戶等級、期間、優先順序、合併同系列）仍然是整條規則共用。
- 剛勾選時，每個商品會先有一個階梯，帶入目前已經填的「數值」和「數量從」（各商品另外指定過價格的，帶入那個價格），再各自修改。
- 取消勾選：回到「所有商品同樣的條件」；「數值」如果還是空的，會帶入各階梯中最小的那個數值。
- 儲存時會檢查：每個商品至少要有一個階梯、「買幾件以上」要大於 0、同一個商品兩個階梯的「買幾件以上」不能一樣、「到」不能小於「從」、數值要填。

### 階梯怎麼算
- **買到哪個階梯就用哪個**：符合的階梯裡，「買幾件以上」最大的那個。例：「10 件以上 90、30 件以上 80」，買 12 件是 90、買 35 件是 80。
- 「到幾件」不填＝以上；填了的話，超過就不再適用那一階（例：只有「10～19 件 90」，買 25 件就不適用）。
- **買不到第一個階梯**（例：只買 3 件）：這條規則不適用，照標準價或其他規則。
- 同一個商品同時符合好幾條規則時，仍照系統原本的設定決定用哪一條（取最低價，或依優先順序取第一條）；階梯只決定「這條規則對這個商品、這個數量」給多少。
- 勾選「合併同系列」的規則，數量仍是用同系列加總來算。

### 開單時
- 銷貨單、客戶訂單、價格試算都會依商品與購買數量，帶出對應階梯的價格；銷貨單會寫「套用「規則名稱」NT$90」（寫的是這個商品、這個數量的價格）。
- 報價單用同一套計價（客戶有歷史成交價時，仍是先用上次成交價）。
- 「再買幾件就有優惠」的提示會算到下一個階梯的門檻。

### 價格等級與折扣
- 有數量階梯的規則，在各等級的畫面會多一列顯示每個商品的階梯，例如「T-RED　10 件起 NT$90、30 件起 NT$80」（有上限的寫成「10～19 件」）。
- 點這種規則會開完整的「編輯價格規則」表單（小表單沒辦法編輯階梯）。

### 價格策略匯入／匯出
- 匯出：「商品內容」會寫成「**料號@階梯**」，多個商品用「、」分隔，階梯之間用「/」分隔，例如 `T-RED@10+:90/30+:80、T-BLUE@5+:95`。
  - `10+:90` ＝ 10 件以上，數值 90；`10-19:90` ＝ 10～19 件，數值 90。冒號後面是數值，依該列的「計價方式」解讀（折數 90 ＝ 九折）。
  - 這種規則的「數量從／到」會是空白（用不到），「數值」放各階梯中最低的數值（參考用）。
- 匯入：同樣寫法即可新增或修改。「計價方式」要填（階梯的數值需要靠它解讀）；「數值」、「數量從／到」可以空白。
  - 也看得懂 `10:90`、`10 件以上:90`、全形的「＠」「：」「／」、`10~19`、`=`。
  - 折數可以寫 `90`、`9`、`0.9`、`9折`。
  - 只有 1 個商品也可以寫成 `T-RED@10+:90/30+:80`。
  - 每個商品後面都要寫階梯（不能一部分商品寫「@單價」或沒寫、一部分寫階梯）；料號找不到或重複、階梯看不懂、兩個階梯的「從」相同，都會在預覽時指出是第幾列、哪個商品。
  - 這一列若同時填了「數量從／到」，會警告「用不到、以階梯為準」；「數值」和階梯最低值不一樣時也會警告。
- 匯出後再匯入同一個檔案，不會有任何變動；階梯、商品的順序不同、內容相同也視為沒變。沒有料號 ID 的新列，內容相同會視為同一條，不會重複新增。
- 舊的寫法（`T-RED、T-BLUE`＋「數值」、`T-RED@80、T-BLUE@85`）照舊可用，不用轉換。

### 注意
- 這一版的階梯是「每個商品各自的數量階梯」；同一條規則裡所有等級仍共用同一組階梯。如果要**每個等級各自不同的價格**（例如批發 80、VIP 75），目前請各建一條規則；要不要做成「等級 × 商品」的價格表，可以再提。
- 有階梯的規則，資料裡會另外存每個商品的階梯，規則本身的「數值」放最低值、「數量從／到」為 0。**還開著舊版頁面的手機，要重新整理（或關掉再開）之後才看得懂階梯**，不然舊版畫面會把這條規則當成「所有商品最低值」的單一價格。
- 舊規則、舊版匯出的檔案都不用轉換；打開舊規則什麼都不改按「儲存」，存下來的內容和以前完全一樣（11 種舊規則形狀逐一比對過）。
- 順手修正：價格規則表單裡，取消「各商品分別指定價格」時，「數值」欄有時沒有跟著更新，現在會即時顯示。

### 要更新什麼
- **網站：換 `index.html`**。Firebase 規則、雲端函式都不用動。（規則多存一個 `prod.tiers` 欄位，現有的規則設定允許。）

### 驗證
- 新增 231 項自動測試：計價（多等級、四種計價方式、取最高符合階梯、買不到第一階梯、有上限的階梯、期間、停用、採購端、合併同系列、同優先序取最低價）、「再買幾件」提示、顯示文字、價格等級畫面、表單（勾選、驗證訊息、複製、增減階梯、編輯舊規則、取消勾選、舊規則轉成階梯、折數寫法、成本加成）、匯出匯入（來回不變、改階梯偵測、各種寫法與錯誤、整列驗證、實際走「匯入檔案」流程）、單據編輯畫面、價格試算、開銷貨單帶入單價。其餘 18 組既有測試全部通過。
- 另外用真正的瀏覽器（手機寬度）看過表單、價格等級畫面的排版，並依看到的結果調整了階梯文字的位置。
- **沒做到的**：沒有在真的 iPhone／Firebase 上操作過；已存在雲端的真實規則資料沒有拿來測（現有規則的行為已用 11 種舊格式比對，沒有改變）。

## 新功能：架位管理、架位 QR Code 標籤、商品架位調整（版本 2026.10.11-bh）

以前每個商品的「架位」是各自手打的文字，容易打得不一致（A-27-2、A27-2、a27-2），要調整也得一個一個打開商品去改。現在有一套架位管理：**先建立架位清單 → 列印 QR Code 標籤貼在貨架上 → 用手機或掃碼槍「掃架位標籤＋掃商品條碼」，商品就放到那個架位**。揀貨輔助、循環盤點本來就依商品的架位排順序，所以調整完立刻生效，不用另外改。

### 在哪裡
- 功能表 →「庫存與商品」：**架位管理**、**商品架位調整**（原本的「架位設定」逐一填寫畫面還在，上面多了兩個捷徑按鈕）。
- 權限：管理員，以及有「庫存」權限的人（倉管）。唯讀帳號用不了。
- 商品詳細頁：「架位」那一列旁邊有「**調整**」按鈕（還沒有架位的商品會顯示「（未設定）」，一樣可以按）；另外會顯示「架位最近調整」（誰、什麼時候、從哪裡到哪裡），以及可以展開的「架位異動紀錄」（最近 20 筆）。

### 1. 建立架位（架位管理）
- 上方四個數字：架位、已放商品、空的、已停用。下面可以搜尋、用「全部／有商品／空的／已停用」篩選；點一個架位，看它放了哪些商品、庫存合計和它的 QR Code。
- **＋ 新增架位**：填架位代碼（例：A27-2）和備註（例：飲料區、二樓、冷藏）；有多個倉庫時要選倉庫。
- 代碼寫法：全形會自動轉半形、各種橫線換成「-」、多餘空白會整理；最長 40 個字，不能有「|」；英文大小寫視為同一個（a-03 和 A-03 是同一個架位，存成你輸入的寫法）；同一個倉庫不能有兩個一樣的代碼。
- **批次產生**：一次建立很多架位，兩種方式：
  - **用格式產生**：大括號 `{ }` 裡放範圍或清單，大括號以外的字原樣保留。`{1-30}` 是數字範圍；`{01-12}` 開頭是 0 會補零（01、02…12）；`{A-C}` 是字母範圍；`{A,B,E}` 是指定清單。
    - `A{1-30}-{1-3}` ＝ A1-1 到 A30-3（90 個）
    - `{A-C}{01-10}-{1-4}` ＝ A01-1 到 C10-4（120 個）
    - `A{001-120}` ＝ A001 到 A120（流水號）
    - `{A,B,E}-{1-5}` ＝ A-1 到 E-5（只有 A、B、E 三區）
    - 畫面上點範例就會帶入。一次最多 2000 個；大括號沒成對、範圍寫反（`{5-1}`）、大小寫混用、清單是空的，都會寫出哪裡不對。
  - **貼上架位清單**：一行一個，或用逗號、頓號、分號隔開；可以直接從 Excel 複製一欄貼上。
  - 建立前會先預覽：「會建立 N 個新架位（另有 M 個已經有了，會略過）」，已經有的不會重複建立。每個架位是一次寫入，數量多時會跳出進度視窗，等它跑完。
- **舊資料一鍵補齊**：商品資料裡已經手打過、但還沒建立在架位清單的架位，畫面上會提示「商品資料裡用到 N 個架位，還沒建立在架位清單」，按「全部建立」就補齊。
- **編輯**：改備註、停用、改代碼。**改代碼**時，放在這個架位上的商品（含已停用的）會一起改成新代碼（會先確認；貼在貨架上的舊標籤要重新列印）。中途失敗會停下來並告訴你已更新幾個、舊架位還在，再按一次即可。
- **停用**：不能再放商品，掃到會提示「已停用」；原本放在上面的商品不會被動。
- **刪除**：架位上還有商品（含已停用的商品）時不能刪，要先移走；刪除後貼在貨架上的標籤就掃不到了。
- **匯出架位清單**：架位、倉庫、備註、狀態、商品數、商品料號（需要有匯出權限）。

### 2. 列印架位標籤
- 入口：架位管理 →「列印標籤」（整批）、某個架位的畫面 →「列印標籤」（單一）、掃描調整畫面的「印標籤」。
- 勾選要印的架位（可搜尋、「全選目前列出的」、「含已停用」），下面設定標籤格式，並且會**即時預覽**：
  - 標籤紙規格：和商品標籤同一組（捲筒 60×40 mm 等、A4 貼紙頁、自訂寬高）；A4 貼紙可以指定「第一張從第幾格開始」（貼紙用過一部分時）。
  - 每個架位印幾張（1～20）、版面（QR 在左、文字在右／QR 在上、文字在下）、架位文字大小（小／中／大）、要不要印備註；有多個倉庫時可選擇要不要印倉庫名稱。
  - 設定會記在這台裝置上，下次不用重設。
- 標籤內容：**架位 QR Code ＋ 大字的架位代碼**（很長的代碼會自動縮小）＋ 備註。
- QR Code 的內容：主倉庫是 `LOC|A27-2`；其他倉庫是 `LOC|倉庫代號|A27-2`。前面的 `LOC|` 是用來和商品條碼、單號分開的，所以掃到商品條碼不會被誤當成架位。
- **第一次請先用 1～2 張試印**，確認標籤紙大小、位置，並且實際用你的手機或掃碼槍掃一次；列印視窗的邊界選「無」、縮放選「100%」、紙張大小要和標籤紙一樣。QR Code 太小會不好掃，標籤紙建議 60×40 mm 以上。

### 3. 商品架位調整（掃描）
入口：功能表「商品架位調整」；架位管理的「掃描調整」；某個架位畫面的「掃描整理」（已經選好那個架位）；商品頁的「調整」（已經選好那個商品，直接進入單品移位）。畫面上方有兩種方式可以切換（會記住上次用的）：
- **上架：先掃架位，再掃商品**。掃貨架上的架位標籤 → 畫面顯示這個架位現在放了哪些商品 → 一個一個掃商品條碼（或輸入料號），商品就放進這個架位；要換下一個架位，直接掃它的標籤。適合整理一排貨架。
- **單品移位：先掃商品，再掃新架位**。掃商品條碼 → 畫面顯示它現在在哪個架位 → 再掃新架位的標籤，商品就搬過去。「不搬了」可以取消。適合零星搬動。
- 掃碼槍（當鍵盤用）、手機相機（「相機掃描」）、「拍照掃描」、手動輸入都可以；輸入架位代碼、料號或品名時，下面會列出選項可以直接點選。
- 每次調整都會出現在「這次調整的商品」，每一筆都有「**復原**」（回到調整前的架位）；架位上現有的商品旁邊有「**移出**」（把商品從這個架位拿掉，變成沒有架位）。
- 掃到屬於另一個倉庫的架位標籤，會自動切到那個倉庫。
- 商品本來就在這個架位：會提示「本來就在」，不會重複寫入、也不會多記一筆。掃碼槍連按兩次、相機連續讀到同一個條碼，也只會寫一次。
- 找不到的架位、已停用的架位、該掃架位時掃了商品……畫面會用文字說明；成功是短的高音、失敗是長的低音。
- 每次調整都會記在商品的「**架位異動紀錄**」：時間、誰、哪個倉庫、從哪裡到哪裡（保留最近 20 筆）。
- 有多個倉庫時，每個倉庫各有一個架位。其他倉庫沒填架位時，揀貨照舊沿用主倉庫的架位（畫面上會寫「現在還沒有架位（沿用主倉庫的 A27-2）」）。

### 4. 和原本功能的整合
- **揀貨輔助、循環盤點**：照舊依商品的架位排順序，不需要設定。
- **商品資料表單**：架位欄可以從已建立的架位清單選（輸入時會出現建議），旁邊有「掃描」按鈕，直接掃架位標籤；儲存時會整理寫法（全形轉半形…），有改動的話也會記進架位異動紀錄。
- **架位設定**（逐一填寫的舊畫面）：同樣可以從架位清單選，有改動會留紀錄；上方有「改用掃描調整」「架位管理」兩個捷徑。
- **備份、還原、清除資料**：架位清單（`inv_shelves`）包含在內；「清除資料」裡架位歸在基本資料。雲端自動備份（`line-functions`）的清單也補上了架位，以及之前漏掉的「組合優惠」「交班」。
- **資料量**：claude.ai 試用版有文件數上限（5000 份），架位每個算一份；批次建立前會先檢查，會超過就不讓建立。Firebase 版沒有這個上限。

### 5. 權限與 Firestore 規則（重要）
- **架位清單**（`inv_shelves`）：沿用原本的規則（可編輯以上的人可以寫），**不用改規則就能用**。
- **商品放在哪個架位**是寫在商品資料（`inv_products`）裡，而原本的規則規定商品只有管理員能改。所以：
  - **管理員帳號**：什麼都不用改，直接能用。
  - **倉管（可編輯、非管理員）要用掃描調整**：規則要多開一小段，只允許他們改「架位相關欄位」（`shelf`、`shelves`、`shelfLog`），商品的其他欄位（名稱、價格、進價…）仍然只有管理員能改：

    ```
    match /inv_products/{id} {
      allow update: if invCanEdit()
                    && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['shelf', 'shelves', 'shelfLog']);
    }
    ```

    更新後的 `firestore.rules`、`firestore.rules.full` 已經包含這一段（放在最後一個通用 `match` 前面，兩段規則是「或」的關係）。把檔案內容貼到 Firebase Console → Firestore Database → 規則 → 發佈即可。
  - 不想讓管理員以外的人調整架位：不要貼這一段（或把它刪掉）。沒有這段規則時，倉管掃描會看到「沒有權限修改商品的架位…」的提示，**不會寫壞資料**。

### 要更新什麼
- **網站：換 `index.html`**（claude.ai 試用版已更新）。
- **Firestore 規則：選用**（要讓倉管也能調整架位才需要，見上）。
- **雲端函式：有部署過 `line-functions` 的話**，換掉 `line-functions` 資料夾後重新部署（`firebase deploy --only functions --project cheunyei-enterprise-system`），自動備份才會包含架位；沒部署過就不用管。
- 還開著舊版頁面的手機，要重新整理（或關掉再開）才看得到新功能；舊版不認識架位清單，但商品的架位資料格式沒變，舊版照常可用。

### 注意
- 一個商品在一個倉庫只有一個架位（和以前一樣）；一個架位可以放很多商品。
- 只有「掃描調整」、商品表單、架位設定、架位改名這幾種方式會留「架位異動紀錄」；用批次修改或匯入商品資料改的架位不會留。
- 架位清單每次開啟系統會讀一次（每個架位算一次讀取）。架位很多（上千個）又常開系統時，請留意 Firebase 的每日讀取額度。
- 標籤要乾淨、平整、不要反光；掃不到時，先試試「拍照掃描」，或在架位管理手動輸入代碼。

### 驗證
- 新增 604 項自動測試：架位代碼整理與比對、批次格式展開（各種寫法與錯誤）、QR Code 內容與解析、管理畫面（建立、編輯、改名連動商品、停用、刪除、篩選、匯出、補齊舊資料）、標籤列印（各種規格、版面、份數、起始格）、掃描調整（兩種方式、復原、移出、多倉庫、重複掃描、寫入失敗、權限不足）、商品頁／商品表單／架位設定整合、備份還原與清除資料。原有的 19 組測試、揀貨單據測試全部通過；雲端函式 68 項測試通過。
- **QR Code 的正確性**：編碼器的輸出，用獨立的解碼器（ZXing 的矩陣解碼）核對了約 5,000 種內容與各種遮罩，全部解得出來；另外把標籤畫成模擬鏡頭拍到的影像（縮放、旋轉、模糊、雜訊）再解碼，也都讀得出來。順帶發現：ZXing 的影像偵測器對「完全乾淨的合成影像」本身就有大約 3% 讀不到（連它自己編出來的也一樣），所以測試改成直接核對點陣內容，不是編碼有問題。
- 另外用真正的瀏覽器（手機寬度）看過各個畫面，並依看到的結果調整排版（掃描調整的兩個方式按鈕、商品頁的「調整」按鈕、標籤清單的高度）。
- **沒做到的**：沒有在真的 iPhone／Firebase 上操作過；沒有拿雲端上的真實商品資料測；**沒有實際印出標籤、用手機或掃碼槍掃過**，所以才請你先試印 1～2 張。
